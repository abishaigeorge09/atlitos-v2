## Deviations found and fixed during this pass

1. **Hex color literal outside token scope**: `packages/ui-web/src/Eyebrow.css` had two hardcoded hex fallbacks in `var(--color-text-tertiary, #8c8072)` / `var(--color-accent, #ff4200)`. The repo's eslint no-hex rule only inspects JS/TS AST literals, it does not lint `.css` files at all, so this slipped past `pnpm turbo lint`. Fixed by removing both hex fallbacks (every consuming app's generated globals.css always defines these vars, so no fallback is needed). Flagging the eslint gap itself for Phase 2: the no-hex rule has a blind spot on `.css` files, the grep gate is currently the only real enforcement there.
2. **Migration version collision, RPCs never reached the database**: two migration files were both authored with prefix `0004` by parallel builder tracks (`0004_admin_verification_rpcs.sql` and `0004_player_and_coach_setup_rpc.sql`). Only the latter was ever pushed to the remote Supabase project; `admin_approve_verification_request` and `admin_reject_verification_request` did not exist remotely even though `apps/admin/src/pages/verification/show.tsx` already called them via `supabaseClient.rpc(...)`, so the admin verification approve/reject flow was silently broken. Confirmed via `pg_proc` query returning zero rows before the fix. Fixed: applied the migration directly via the Supabase MCP under a new non-colliding version (`0007_admin_verification_rpcs.sql`), renamed the local file to match, and closed an anon-execute gap in the same statement (Supabase's default privilege grant gives `anon` EXECUTE at function creation time regardless of an in-migration `revoke ... from public`, the same pattern `0005_tighten_rpc_grants.sql` already had to fix for the sibling RPCs; added explicit `revoke ... from anon` this time instead of needing a follow-up migration). Updated the three stale file-path references (`docs/architecture/API-MAPPING.md`, `apps/admin/src/pages/verification/show.tsx`, `apps/admin/src/pages/verification/list.tsx`). Verified post-fix: `has_function_privilege` shows `anon=false, authenticated=true` on both functions; security advisor no longer flags them as anon-executable.
3. No other cross-agent prop mismatches found; `pnpm turbo typecheck build lint` was already fully green on first run before any fixes, meaning builder tracks coordinated cleanly through packages/types and packages/theme as intended.

## Fix cycle (orchestrator hand-verification, this pass)

Four issues found by hand-verifying the running apps in Chrome, all fixed, `pnpm turbo typecheck build lint` re-verified 24/24 green after each, `npx expo export --platform ios` and `--platform web` re-verified green.

1. **BLOCKING, `apps/mobile`: accent Tailwind color key collision.** `apps/mobile/scripts/gen-tokens.ts`'s `rawColorBlock()` deliberately skipped emitting a raw `accent` color utility because it collided with the shadcn/react-native-reusables compatibility slot also named `accent` (which is a TINT, `hsl(var(--color-accent-tint))`, upstream shadcn's hover/pressed background convention, not a brand color). The slot silently won the collision, so every `bg-accent`/`text-accent`/`border-accent` in the app (Button primary, StatusPill-adjacent chips, active tab indicators, progress fills, Input focus outline, Stepper, BillSummary donation checkbox, ...) rendered the pale accent tint instead of the true ember brand accent (`#E46136`, hsl `15 76% 55%`). Fixed: renamed the shadcn compat slot to `accent-soft`/`accent-soft-foreground` (CSS vars `--accent-soft`/`--accent-soft-foreground` in `global.css`, Tailwind key `accent-soft` in `tailwind.config.js`), freeing `accent` for the raw brand palette. Audited every `bg-accent`/`text-accent`/`border-accent` call site in `apps/mobile/src/components` and `src/app`: all were already semantically correct per DESIGN-LANGUAGE.md (primary CTAs, active tab, selected chips, progress bars intended as true ember), none needed a class change, only the token wiring was wrong. Nothing in the codebase reads the shadcn tint slot today, `accent-soft` is kept only for future shadcn-pattern compatibility. Verified in exported web CSS: `.bg-accent{background-color:hsl(var(--color-accent))}` with `--color-accent:15 76% 55%`.
2. **BLOCKING, `apps/mobile`: dev gallery theme toggle threw on web.** `src/app/dev/gallery.tsx` and `src/app/dev/tokens.tsx` called React Native's `Appearance.setColorScheme(...)` directly, which react-native-web does not implement (throws, surfaced as an error toast) and does not affect nativewind's `dark:` class resolution on web even when it doesn't throw. Root cause was two-layered: (a) the toggle used the wrong API, (b) `src/theme/use-theme-colors.ts` (the StyleSheet/JS token path almost every screen and component uses) read React Native's own `useColorScheme`, a different, unsynced source of truth from nativewind's web-only `dark` class state, so on web the className-driven and StyleSheet-driven halves of the app could independently disagree about which theme was active. Fixed: both dev screens now call nativewind's `colorScheme.set()` (from the `nativewind` package); `use-theme-colors.ts` and `_layout.tsx`'s status bar now read nativewind's `useColorScheme()` instead of React Native's, so every component, regardless of which of the two styling systems it uses, agrees on the resolved theme on both web and native. The gallery toggle cycles system/light/dark with the current resolved mode labeled ("System (dark)", "Light", "Dark"); "system" resolves to a concrete light/dark before calling `colorScheme.set()` (never passes the literal `"system"` through) because nativewind's web runtime clears the `dark` class rather than checking `prefers-color-scheme` when given `"system"` directly under the `darkMode: "class"` strategy this app uses, an upstream nativewind/react-native-css-interop behavior, not a bug introduced here.
3. **Dark mode contrast.** Input label and ghost button text were already correctly wired (`text-text`/full ink on both), not the bug as initially suspected, likely a symptom of issue 2 (className vs StyleSheet theme desync) rather than a wrong token choice. Swept the full component library for `textTertiary` text (not icons, which only need the 3:1 non-text minimum) sitting on a `surface`/`card`/`surfaceMuted` fill in dark mode: `textTertiary` on those surfaces measures 3.98-4.33:1, below the 4.5:1 AA minimum for normal text (only passes against the base `bg`, at 4.66:1). Fixed by switching the affected instances to `textSecondary` (7.0-7.6:1 on those same surfaces): `MilestoneChip` unearned label, `UPACard` "of ₹goal", `CoachCard` distance, `ProductCard` struck original price, `PriceText`'s `strike` color, `EarningsHeader` (Balance/This month/Pending labels, the whole header is a card), `CoachProfileSheet` (5 overline/caption labels, the whole sheet is a `surface` fill), `BillSummary` molecule's "muted" emphasis row (used inside card-wrapped callers like `BookingConfirmation`), `_shared.tsx`'s `Stepper` step number (circle fills `surfaceMuted` when neither done nor active), `CommentsSheet` comment timestamp (sheet is a `surface` fill). Left `textTertiary` alone where the immediate background is the page `bg` or genuinely ambiguous/caller-determined (bottom nav, timeline/transaction rows with no own surface fill, calendar weekday headers), those measure 4.66:1 against `bg`, a technical pass. No new hex introduced, every fix reuses an existing `@atlitos/theme` token per DESIGN-LANGUAGE.md's "tokens only" rule.
4. **`apps/portal-court`: 4 dev overlay errors on the landing page.** All four were the same Base UI warning ("A component that acts as a button expected a native `<button>`... set `nativeButton` to `false`") on the 4 header/hero `Button` instances in `src/app/page.tsx` that use `render={<Link href="..." />}` to render as a Next.js `Link`/`<a>` instead of a native `<button>`. Fixed by adding `nativeButton={false}` to all 4. Verified clean via a live `pnpm dev` + browser console check, zero console errors after the fix.
